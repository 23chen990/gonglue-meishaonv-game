# r4.2 第一选择与选项数量专项审查（2026-10-13）

## 可复现的结果

- 开场真正的第一个行动是 `ENTRY_WAKE` 的 **3 选 1**：照原著留守设备箱、找蓝标 U 盘抢救首演、先查错版来源。原著第一次钢琴救场和第七天被清退的因果已提前展示；无需按“继续”才能选。
- 为降低 360px 手机上三行长标题的阅读成本，首页显示简短动作名，同时保留带完整剧情描述的按钮 `aria-label`。这属于呈现层变化，不改正式 `choice.id`、效果和分支。
- 重新运行 `npm run verify`，正式故事为 **228 场 / 751 个底层选项**，历史结局与证据分支仍以现有回归约束保护。
- `tools/audit-choice-count.mjs` 从 751 条选择的真实命令前缀回放得到 279 种“场景 + 当前可选动作集合”，其中 16 种状态有 5–6 个内部可选动作。数据详见 `qa/current/r42-choice-count-audit.json`。
- `tools/test-ui-r4.py` 使用真实浏览器控件遍历这些状态：每组最多显示 **3 个可点的剧情选项**，切换上／下一组不增加历史命令；重新导入同一状态也可再次选择。这是**屏幕上限**，不是把全部正式候选压缩到 3 个。
- 本地注入 DOM + 显式模拟存档 14 项 PASS；四人路线普通触控 95 个输入 + 回退 PASS。**GitHub 真 HTTP 原生浏览器需对本提交另行检查 CI**。

## 与用户“最多 4、通常 2–3”的要求之间的边界

当前 **单屏** 最多 3 个动作，满足手机操作密度；但若把“一个剧情决策总共不超过 4 个候选”作为严格规则，则 **尚未完全满足**，不能混为一谈。主要原因是角色关系承诺、四人邀约、事业计划、六种第七天自救办法等存在真正不同的长期结果，直接删选项会切断正式结局。

推荐的下一轮设计措施：将 16 种高选项状态逐一改造成有剧情意义的二段决策，例如先选“向前合作／独立承担／暂时退出”，再只展现这一方向下的两种具体做法；第一个子选择需要有文字反馈与情节依据，不能把纯翻页谎称为新决策。修改后必须同步更新普通命令见证、承诺/同意状态、四人结局与时间轴，不能只靠 HTML 视觉通过验收。

## 测试边界

- 文件内 witness 回放是真实引擎命令，而非任意注入内部旗标；仍不覆盖状态空间的所有组合。
- `test-ui-r4.py` 的 fixture 浏览器借助内存中注入的 HTML 与模拟 localStorage，不证明本机原生 HTTP 浏览器持久存档。
- 真人是否理解“原著／改写”的差别、四位女主的吸引力、Android/iOS 实机手感以及变现/上架均为 NOT_TESTED。
