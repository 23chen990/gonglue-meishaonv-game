## 先说结论

**不要先换皮，也不要先写几百条人生事件。先把“家况与纪念物 → 有代价的选择 → 后果回来找你 → 独特判词 → 想换一种活法”做实。**

我建议的定位是：**乡土年代背景下、有因果、有遗憾、有不同去向的人生重开游戏**。借《人生重开模拟器》的开局组合、条件事件和重开欲望，保留本作主动做选择、人物关系和卷宗质感的原创优势。

## 三、建议改成什么体验

### 1. 开局：不是抽几个数，而是拿到一个“这一局试什么”

仍保留家况签与纪念物，不额外叠一轮天赋抽卡。首屏增加一个清晰的短局结构：**起点 → 六次决定 → 人生判词 → 带走经验**。

纪念物卡强调它倾向打开哪类机会，再展示属性；家况不仅改数值，还要在后续人物、可遇事件或补救机会中被提及。先用现有数据和事件验证这一点，不新增第五项常驻系统。

可在已具备真实内容的路线中提示一个可选愿望，例如“试着靠手艺打开一条路”；它是本局的方向，不是新任务面板，也不是唯一定义成功的标准。

**本轮切片硬边界：**“愿望”只允许由现有家况、纪念物或 flags 派生为展示文案；不得新增属性、资源、必选决策、独立 UI 面板或持久化字段。机会/风险标记必须指向既有 event、choice、flag 或 pending echo，不能凭空承诺不存在的玩法。若无法从现有状态真实推导，先不显示；若需要新系统，退出本轮范围并单独审批。

### 2. 中途：少做数值题，多做互有代价的决定

六次选择先不加长。重点打磨三类锚点：**读书与家务、手艺与眼前收入、离乡机会与家庭承诺**。每个锚点有三个要求：

1. 做之前看得懂当前代价与涉及的人，不预先公布全部未来剧情。
2. 做之后立即看见状态变化或人物反应，而不只闪一个加号。
3. 后面至少一次具体回访，改变一段遭遇、一个可选行动或最终判词证据。

**原创设计示例，尚未实现：**

> 你答应帮村里的运输队修旧车，因此错过了这次跟车进城的机会。下一次进城收货时，运输队愿意替你留一个位置——不是凭空增加“乡情”，而是旧承诺变成一条新的路。另一路选择立刻进城，可较早获得交易机会，但不能同时获得这份人情。

先复用现有“修理/进城/协作”题材承载这种因果，不因为示例而立刻另开大型车辆系统或交通小游戏。

### 3. 压力：来自机会和承诺，不来自莫名其妙地死掉

| 压力 | 玩家怎么提前看见 | 怎么加深 | 错失后怎么办 |
|---|---|---|---|
| 机会窗口 | 路线节点、临近刻度、机会卡变形/变色，并配短标签 | 从还有选择，到临近兑现，再到进入不同后续 | 错过当前愿望但仍有替代道路，不直接结束人生 |
| 筋骨/家底的透支 | 状态条低位标记、风险图标、选择前后差异 | 后续行动可用性或代价改变，而非偷偷提高全部阈值 | 可以通过有代价的行动缓解；穷并不等于没有尊严的失败 |
| 未兑现的承诺 | 小型回响标记：来源选择 + 预计几个决定后回来 | 标记进入待兑现，再实际影响人物或机会 | 玩家能解释“因为我当时做了什么”；局内和下局均有修正方向 |

全部节奏由决策推进，不增加实时倒计时；阅读慢不应受罚。关键规则不能只藏在小字里，也不能只靠红绿颜色。

### 4. 结算：从“这一章结束了”，改成“这一局我活成了谁”

这是第一优先级。现有判词应成为封卷主标题，下方固定三个区域：

- **这一局的身份与一段原创收尾**：先把引擎已有结果接到画面，不另造一套评分。
- **两条“为什么”**：具体选择 → 后来发生的事 → 这次判词；显示有成就也有遗憾的轨迹。
- **下一局能试什么**：明确一项继承的作用与一条尚未走过的机会，不只是“属性 +1”。

不再用未兑现的“下一章会继续”作为唯一回报。不把财富、身份高低或家庭关系换算成唯一人生总分。现有“田埂松动……”可以保留为章节副标题，不能压过真实结局。内部字段 `economy`、`skill`、`bonds` 等不得出现在给玩家的继承说明里。

### 5. 重开：新东西必须和上局有关系，而不只是再投一次骰子

近期先落实“**看见上局痕迹 + 知道一条没走过的路**”，仍使用现有继承和事件池。

- 接通上局事件历史：在满足当前状态与时间逻辑的候选中，优先提供未见的合适事件；不为换新强行破坏因果或发明必然不同的剧情。
- 继承卡标明会影响哪类机会，并在新局开头以同样图标对照展示；保持有上限，不做无限刷属性。
- 封卷可给一句未走道路的提示，但不能剧透整条最优路线。
- 前两次决定内应看见至少一处由上局经历驱动的具体变化：合适的新事件、可用行动或人物回访。**仅“这是第二局”、颜色变化、数值 +1 不算兑现。**
- 若受逻辑条件限制不能立即给新事件，必须给真实的可选路线或回访；若三者均不可能，标记该配置验收失败，而非降低标准。

## 四、第一轮做多大

### 必做：救活已有六步垂直切片

1. 锁定当前内容契约：逐项对齐家况、年份、事件、flags、效果与旧设计；保留差异审阅记录。
2. 显示真实判词、两条因果依据与可理解的继承。
3. 回响具备来源和兑现状态；先打磨三组 A/B 锚点回访。
4. 让真实 restart 路径读取上局信息，交付可见且合乎状态的差异。
5. 用首屏结构、机会/风险状态和结算层级改善体验；保留卷宗视觉，不重做整套美术。

### 先不做

不新增第五属性，不扩几百条事件，不引入完整家谱、城镇经营、养成日程、抽卡商业化、重后端或新引擎；不以广告解锁唯一好结局。不开独立小游戏来掩盖主循环问题。

### 通过第一轮后，再决定扩不扩成一生

若玩家已经能说明“我下局想换哪条路”，再扩到**离家 → 立足 → 承担 → 回望**四阶段。可先用两条主路打通完整默认流程，再补内容，避免先写几百条中间事件却仍无收尾。退休、交棒或回望都可以结束一局，不必靠死亡定义终点。

此阶段涉及默认旅程、存档与内容合同变化，必须重新批准；不自动继承本提案的执行授权。原材料里出现过的 12—15 分钟不能直接当作本次已验证时长。先记录人工实际阅读与选择时长，再决定长短；不以自动化点击用时估算真人节奏。

## 五、怎样知道改好了

**工程轨与玩家体验轨分别验收；任何一轨 BLOCKED 都不能宣布完成。** 下表是未来验收目标，不是本次已达到的结论。

| 闸门 | 最小证据 | 不接受的替代证明 |
|---|---|---|
| 真实默认入口 | 启动→六次选择→真实判词→继承→第二局，全程正常输入；列出 `index.html → src/main.ts → src/game.ts / chapter-data.ts` 等实际入口 | 只改 artifact、只跑 debug reset、旧逻辑仍在默认页 |
| 判词可见且可达 | 枚举现有六个判词逐一核实可达性；自然路径结算显示正确标题与因果证据；无法到达的判词保持 BLOCKED | state.verdict 有值或单测通过，但 UI 永远同一句话 |
| 三组锚点因果 | 每组 A/B 各有一次后续可见差异与回访，至少保留按钮点击轨迹和截图 | 只改属性、换形容词、走了兄弟分支 |
| 回响准确 | 有来源；该到时兑现一次；刷新、恢复不重复；观察到具体来源分支 | 只证明数组里有 pendingEchoes |
| 真实复玩 | 360×800、390×844、844×390 均从封卷进入第二局；前两次决定内有可归因到上局的内容/行动/人物回访差异 | 独立实例用 runNumber/seed 构造“第二局”；换标题、颜色、统一提示或只显示 +1 |
| 压力可理解 | 正常输入分别走满足、错失、补救分支；事前有信号，事后能找到原因和恢复动作 | fixture 截图、判词自报通过或堆解释文字 |
| 小屏可读 | 360×800、390×844、844×390 的行动、风险、回响、封卷和重开逐分支检查；必要时补 320 宽 | 只有页面不横向溢出，没有感知与触达检查 |
| 保存与升级 | 锁定旧档迁移策略，验证刷新、恢复、继承上限与清档语义；不能静默丢掉旧玩家档案 | 因为在 fresh browser 可玩就认为存档安全 |

另安排至少 5 位未参与开发的目标玩家做两局探索性试玩，观察并询问：第一次想做什么、哪次决定让后面变化、结局为什么发生、下局准备换什么。**建议的试验门槛**：至少 4 人能举出一个真实因果，至少 3 人能提出并自主尝试另一条路径。此小样本只帮助决定是否继续，不是留存预测或统计显著性证明；无人自发想重开时先回到玩法，不继续加事件。

复玩另附机器可核验的 **provenance matrix**：记录首局 eventIds/choiceIds、真实重开后保存的 `previousRunEventIds`、第二局前两节点 eventIds/choiceIds/可见回访，以及筛选或回访使用的历史来源。工程轨可以只读检查存档并验证选择因果；自然轨仍只用普通输入、不得状态注入。用固定随机源的独立工程对照隔离历史作用，但绝不能以该对照替代真实 UI restart。当前横屏仅一局，横屏重开和触达仍未覆盖。

## 六、实现顺序与职责边界

| 顺序 | 产物与责任 | 进入下一步的条件 |
|---|---|---|
| A：确认方案与锁定内容 | 主策划确认本提案；源数据/批准设计差异表；明确哪些旧约束保留 | 当前内容唯一、可追溯；本次不覆盖旧批准文件 |
| B：最小问题包与测试 | QA 把结算不可见、因果不可追踪、真实复玩未兑现变成已验证问题；先补失败测试 | 每项有目标对象、状态分支、复现、验收与最少相关文件 |
| C：六步切片修复 | formal-fixer；按已有工厂、存档和 stage 机制执行，不新造并行编排层 | 每次尝试有新证据假设、一次构建；保留线程与 attempt 记录 |
| D：双轨复验 | Playwright 工程验证与新浏览器自然输入/感知验证；主线程验收，Luna 可只读独立复核 | 精确分支通过，不能用单测或修复代理自报代替 QA |
| E：决定是否扩张 | 根据两局体验证据决定继续原切片、调整设计或扩大人生跨度 | 没有确定的重开价值则停止扩产 |

选 **formal-fixer**，不选 direct-builder：本案涉及核心体验、选择后果、跨局记忆、可能的存档变化，不能作为一个局部 UI 小补丁结案。**本轮未进入正式 FIX、未增加修复次数、未声称问题已修好。** 将来若确实只需窄补丁，也保留正式 QA 与复验义务。

## 七、技术与发布边界

技术建议前已完成本轮 `open-source-research.json`，通过现有 Zod schema。已重新获取两项固定 revision 的直接 MIT 许可证证据：inkjs 与 Life Restart/remake，**本次均不批准作为新增运行时依赖**。前者不能替代玩法设计，后者与竞品内容强耦合；先复用本 run 自有 TypeScript 状态/数据/呈现分层。维护和安全风险为保守待审计判断，不是漏洞结论。

延迟回响先尝试从既有选择历史和队列派生来源视图，跨局记忆读取既有历史；事件候选保持阶段和条件约束，再评估未见内容。A 阶段差异表须证明仍是四项属性、六次决定，且愿望不改变存档版本。确需新增回响持久化字段或改变存档版本时，先单列最小扩展与迁移方案取得范围批准，再先测试后实现；不得把“提示文案”当作隐蔽加系统的理由。本轮不改任何实现。

浏览器仍是开发验证。微信、抖音、TapTap 三端必须分别具有本 run 内的适配、配置、测试、真机 QA 和构建输出；本轮没有三端发布证据，不能标成可上架，也不提前替平台选定未经验证的新引擎。

## 八、留给下一轮的唯一决策

**建议批准的范围：只做 A—D，让已有六步切片真正做到“选得明白、结得不同、重开有理由”。** 先不批准扩大人生跨度或事件产能。
