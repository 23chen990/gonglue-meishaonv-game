## 03｜问题分级与修改顺序

### P0：发布阻断

运行崩溃；主流程卡死；正式结局不可达；状态越界造成错误路线；刷新或双击重复结算；读档错位或损坏存档被清空；拒绝后仍执行不可逆行为；缺失关键条件却进入不成立剧情；资源缺失使正文或选择无法使用。发现一个即修一个并补复现测试。

### P1：体验核心问题

玩家不知道当前想完成什么；选项文字与执行行为不一致；所有选项明显只有一个“正确答案”；重要选择被后文遗忘；角色突然换立场；大量场景不改变信息、关系或局面；结尾不回应主要冲突。P1 不等于代码异常，但必须在发布候选中逐条关闭或明确缩减内容范围。

### P2：局部表达与便利性

个别重复形容、非关键过场偏长、标签不一致、轻微样式问题。不得为了处理 P2 延后 P0/P1，也不得把所有抒情句一刀切删除。

问题记录采用：`问题ID / 类别 / 证据 / 触发路径 / 玩家损失 / 修改文件 / 修改内容 / 回归用例 / 状态`。不填空泛的“提升沉浸感”，要写例如“选了暂不答应，却在下一节点标记 accepted=true”。这只是问题格式示例，并非已发现的仓库问题。

## 04｜剧情结构：让玩家在具体事情里认识角色

### 4.1 开场改造目标

把“玩家现在要做什么、为什么不能完全置身事外、眼前是谁”放进开场可见行为中。建议在前 2—3 屏内给出第一个有信息依据的选择；这是本次编辑目标，不是经验证的行业转化阈值。安静日常也可以成立，不需要强行加事故、倒计时或威胁。

先发生一件需要应对的小事，再补理解它所需的背景。不要先介绍全部世界观、人物档案和数值系统。开头的选项至少改变对话方式、行动分工或眼前结果，随后立刻让对方作出不同回应。

如果原作已经有有效钩子，保留并精简铺垫，不因为“重写”而重写。新开场必须接回原作可验证的因果链，不能为刺激而引入后文无法收束的事件。

### 4.2 每个场景只承担一个主任务

场景可以同时有情绪、人物和信息，但要明确主任务。例如“确认对方愿不愿合作”“发现此前理解错误”“兑现上次承诺”。如果一场戏的唯一作用是重复“她很特别”，合并或删除；如果它创造了新的相处方式，即使没有大事件也应保留。

每场完成这段检查：谁想得到什么？对方为什么不立即答应？玩家能怎样介入？结束时哪件事发生了变化？下一场为什么必然或合理发生？答不出来的场景不靠加形容词补救。

### 4.3 减少拖沓的具体操作

同一事实第一次出现完整交代，之后只使用必要的短回指。旁白已经写出的情绪，不再让人物用同义台词解释一次。合并连续的行走、开门、坐下、看窗外等没有决策意义的点击。将长背景说明拆到玩家需要作决定的时点；可选资料不能成为主线理解的唯一入口。

对每个候选删除段落标注删除理由及被保留的信息位置。不得“删掉 30% 字数”作为唯一目标。删减后的前后连接、语气变化、时间消耗和条件触发必须重新核对。

### 4.4 中段与结尾

中段要让开场建立的相处方式受到检验，而不是不断认识新人、不断埋新谜。至少让一个早期选择以行动、称呼、分工或承诺兑现方式回来。关键转折需要前置线索和人物动机，不依赖突然失联或所有人集体不解释。

结尾回应本线主要问题：事情怎样结束、双方关系怎样改变、玩家的哪段行为起了作用、还有什么明确未解决。可以留余韵，不能用“故事才刚刚开始”代替本次故事的收束。

## 05｜逐场改写卡：必须真正落到源文件

每个场景建立一张记录，推荐放在 `docs/release-audit/scene-rewrite-log.md`。

字段包括：真实场景 ID；原文位置；当前场景目的；人物进入时的知识；需保留的事实；问题；决定（保留/局部改写/合并/删除）；完整新文本；新选项；各选项即时回应；状态变化；延迟回调位置；新出口；对应测试。

处理顺序：先锁定事实，再写对白，再写选项，再写分支反馈，最后读一遍所有进入路径。不要先写一段漂亮对白，再反过来改事实以配合它。

必须同时检查“单条路线连贯性”和“跨路线承接”。合流场景可共享内容，但涉及此前做法时必须使用对应变体。例如已道歉、未道歉、尚不知道此事，不能共享一句默认已经道歉的台词。

关键场景应给完整替换文本，不允许只写“这里让角色更有魅力”。普通场景可局部改写，但要明确替换范围。每个删除节点都要修复跳转、存档定位、回放、章节索引和资源清单。

## 06｜选项：让人想点，也让点击值得

### 6.1 三类选择分别处理

实质选择：改变行动、信息、资源、关系承诺、路线或结局条件。需要可追踪后果。

表达选择：选择说话方式或主角态度，可以重新合流，但应有不同的即时回应；不必每句都加好感。

继续阅读：只有一个合理动作时，显示继续，而不是伪装成两三个同义选项。不能为了节点统计好看而增加点击。

不要把所有表达选择强制改成巨大分支；也不要把所有实质选择降格为换一句台词。Choice of Games 的官方设计文章区分了后果、决策依据与分支规模，作为方法参考 [S1]；本项目是否存在相应问题仍需源码核实。

### 6.2 选项必须表达玩家真正授权的动作

推荐“动作 + 对象 + 必要的已知代价”。例如“先听完她的方案，再决定帮哪一部分”，比“温柔地回应”更可执行。不要用“相信她”包装公开秘密、擅自承诺或肢体接触等额外行为。

重大风险在选择前提示风险类型，不泄露全部剧情答案。例如“会占用今晚剩余时间”“将当着其他人说明”。不可逆行为可以二次确认，但普通对白不要每次弹确认。

关键选择呈现 2—3 个各有理由的方向即可。这是可读性建议，不是所有场景的固定数量。危险、冷淡或自私选项也可以存在，但不能把尊重他人写成必胜按钮、把拒绝写成无聊或羞辱性惩罚。

### 6.3 后果必须落地

为实质选项建立选择账本：`choice_id / 选择前已知信息 / 授权动作 / 即时结果 / 状态写入 / 后续读取位置 / 收束`。找不到后续读取位置的状态变量应质疑其存在；不可只在调试面板里改变数字。

短期反馈优先在紧接着的场景体现。延迟后果指定具体回调场景，不写“后面会有影响”。表达选择的不同回应也要能在实际 UI 中看见，不能只存在于数据中。

### 6.4 解决两类伪分支

文字不同，状态、下一节点和所有后续表现都相同：改成表达选择并补回应，或者合并成继续。

状态不同，但永远没人读取：删除空变量或增加与原剧情相符的真实回调。不要为了证明后果存在，在结尾硬贴一行无关成就。

同目标节点不等于假选择；不同目标节点也不等于真选择。必须比较完整状态与可见后果，而不是只数箭头。

## 07｜人物、感情与台词去 AI 味

### 7.1 角色声音从真实设定中提取

为每位原有角色记录：当前目标、擅长什么、最不愿被怎样对待、常用句式、开玩笑方式、面对冲突的做法、允许改变的部分。每条附 2—3 处原文或行动证据；不要凭角色立绘套“傲娇”“病娇”等标签。

同一意思让不同角色用不同方式说。有人先讲做法，有人先问原因，有人用玩笑掩饰不安；但不要让每个人都重复同一个作者的哲理。重要角色必须有不围绕主角运转的目标，也应偶尔主动提出邀约、拒绝或解决方案。

### 7.2 保留情绪，删除空泛解释

重点标记但不自动删除：连续“微微、轻轻、仿佛、某种、说不清、命运、救赎、你终于明白”；反复“不是……而是……”；动作后跟三句抽象解释；互不熟悉时突然长篇心理剖白；一问一答都像演讲。

修法是找到此刻具体发生的事、人物真正想问的问题和不愿直说的部分。抽象情绪落到可观察行动、物件变化、称呼变化或一句有对象的请求。保留真正有铺垫的沉默、抒情和重复，不用“短句全部替换”制造机械口语。

### 7.3 恋爱或多角色路线确实存在时

区分好感、信任、合作和明确的关系意愿，不默认它们都是同一根数值条。优先利用既有状态；仅为必须表达的区别新增变量，避免突然扩成复杂养成系统。

没有拒绝不等于同意；尚未询问、明确拒绝、明确接受应可区分。拒绝邀约后，不得合流到已赴约的亲密对白。道歉可以打开修复机会，不能瞬间抹除伤害或自动获得恋爱奖励。主动尊重对方仍可以产生幽默、张力和吸引力，不必写成道德测验。

关系升温要依靠共享经历、互相理解、主动回应与承诺兑现。不要靠“正确按钮连续加分”突然告白成功；也不要因一次普通玩笑永久锁死好结局，除非风险与后果在原剧情中清楚成立。

如果实际作品并非恋爱结构，不添加这一套系统。仓库名称不是足够的设定证据。

## 08｜逻辑核查：时间、知识、物件与动机

### 8.1 事实账本

事实记录采用：`fact_id / 内容 / 确认来源 / 可靠程度 / 首次可知场景 / 知情角色 / 是否可被后文推翻`。传闻、角色说法、主角推测、客观事实分开。任何反转必须解释为什么旧信息有限或不可靠，不得悄悄改写已确立的客观事件。

### 8.2 知识不能穿帮

玩家在另一条路线看到的内容，不自动成为本周目主角或当前角色的知识。问出某个专有名词、指出某人说谎、使用某项证据之前，要有本路线的获取来源。拒绝看资料后不能继续引用其中细节。

如果作品没有推理或证据机制，不新增侦探系统；这里检查的是任何叙事都可能出现的知识先后关系。

### 8.3 时间与位置

列出关键事件的先后与可用时间。出行、调查、交谈和承诺是否消耗同一时间预算须统一。不要在一条路线里同时出现在两个地点；时间耗尽后不能靠返回菜单复原。没有时间玩法的作品使用事件先后表即可，不强加倒计时。

### 8.4 物件与责任

唯一物品记录持有人、交接、损坏或消耗；已交出去不能在下一幕再送一次。承诺记录承诺者、对象、内容与截止条件；结果归因不能把玩家没做的事算给玩家，也不能让缺席角色知道现场细节。

每次改写后检查：是谁做的、谁看见、何时发生、为什么这样做、有没有能力做到、代价由谁承担。不要只检查句子通顺。

## 09｜状态与选择提交：一次动作只生效一次

### 9.1 单一权威入口

定位真实引擎的选择提交入口，将合法性检查、状态变更、跳转和历史记录放在一致的事务边界。UI 禁用按钮只是辅助，不代替状态层校验。

概念顺序：读取当前 run 与 revision → 校验 decision_instance_id、choice_id 和前置条件 → 计算下一状态 → 检查不变量 → 接受一次提交 → 更新节点、历史与可恢复快照 → 反馈保存状态。异常时不得留下半套状态，也不得已扣资源却仍停在旧选择。

一次决策实例与 choice_id 不同。同一选项在后续合法循环中可以再次出现；同一个已提交实例的重复点击必须无效。去重键不能只用全局 choice_id，否则会错误阻止合法重访。

### 9.2 刷新、返回与重复进入

选择结果不要放在会重复运行的渲染生命周期里。读档或返回场景必须恢复状态，不再执行奖励。选择前存档重选，必须先回到选择前完整状态，不能保留上一条分支的标记。

异步操作期间的旧按钮、快捷键、连点和迟到回调都携带预期 revision；发现状态已经前进则拒绝旧操作。若有随机判定，保存确定性种子或已结算结果，不能刷新重掷到想要的结果；没有随机系统就不新增。

### 9.3 run 状态与收藏记录

本周目的关系、物品、路线和知识，与跨周目的已读文本、结局收藏、设置分开。开始新游戏清空前者，不误清后者；也不能把收藏中的结局信息当成本周目的故事条件。导入存档后同样检查隔离。

## 10｜存档和恢复不能靠运气

检查存档是否包含稳定节点 ID、状态、当前决策实例、必要历史、schemaVersion、storyVersion，以及已有随机系统的确定性状态。字段应依据真实引擎精简，不能机械增加无用数据。

保存前序列化并校验，写入失败显示真实状态；保留最后一个验证成功的快照。恢复时先验证结构和版本，再安装到运行状态。损坏存档保留供导出或诊断，不自动清空全部存档。新开局覆盖需要明确动作。

剧本删节点后要有旧 ID → 新入口的明确迁移；只有剧情与状态语义兼容才能迁移。无法安全继续时保留原数据并说明不兼容，提供明确的新开局入口，不能默默跳章或重置好感。

浏览器版必须覆盖存储被禁用、写入异常、隐私窗口、跨标签页和版本更新。MDN 明确说明 localStorage 可因策略或来源问题抛出 SecurityError，file:// 下行为也不应作为可靠存档保证 [S3]。实际项目若不用 localStorage，测试对应真实存储层，不强行替换。

## 11｜点击手感与阅读界面

### 11.1 防误触

文字正在逐字显示时，第一次点击只完成显示，不顺便选中刚出现的选项。持续按键、长按和双击不能跨越两次决策。页面滚动松手不能触发底部选择。处理实际事件顺序，不使用任意延时掩盖问题。

提交后立即给清楚的视觉反馈；新内容替换时让玩家知道选中了什么。焦点不能偷偷落到下一屏的默认选项并因同一次回车触发。对话记录查看是只读动作，不执行剧情副作用。

### 11.2 阅读与导航

按真实平台检查正文行宽、字号、说话者标识、段落分屏和长选项换行。移动端最后一个选项必须能滚到并完整点击，不被固定底栏或安全区遮住。建议按钮可点击高度至少 44 CSS 像素，作为本项目设计目标，不冒充合规认证。

键盘 Tab/Enter 可操作，焦点清楚可见；关闭弹窗后回到合理位置。字号放大、减少动态效果和关闭打字机效果不影响逻辑。系统静音或音频失败不应阻断文本推进。

### 11.3 重玩是减重复，不是删内容

已有文本可快速跳过，未读文本或新变体应停下。已读键考虑稳定文本片段及相关内容版本，不只看节点 ID；一个节点的新条件台词不能被误判为已读。章节回放只读与重新开始该章要区分，重新选择应从正确快照分叉。

没有这些功能时，先确保继续、存档和结局返回可靠，不在上线前强加复杂剧情树界面。

## 12｜结局、路线和完整体验

每个发布结局至少有一条从干净新开局抵达的证据路径，附选择序列、终态和对应正文。进入条件、显示条件与结局收藏条件必须一致。互斥条件同时成立时有明确优先级，不能靠数组顺序随机命中。

相同结局不同前史需要正确的回指。关系结局不替代事件结局，事件成功也不强制恋爱成功。普通、错过或分开结局都要有完整的一场收束，而不是一句“好感不足”。不得用羞辱玩家或重播漫长公共线作为主要惩罚。

结局完成后保存收藏成功与否真实可见；返回标题、重玩和查看记录都可用。预告、后日谈或后续章节若尚未完成，不得成为当次体验唯一的情感回报。

## 13｜检查工具：能查什么，不能查什么

### 13.1 已提供的工具

`tools/storycheck.py`：Python 3.10+ 标准库实现，只读入 storycheck/1 格式 JSON，不执行故事代码。不需要给它 GitHub 密钥，也不需要联网。

它检查严格字段与类型、重复 ID、不存在的跳转目标、条件变量、状态边界、带状态可达性、不可点击选项、不可达结局、节点前置条件、声明的不变量、无选项死路，以及无法到达任何结局的可达状态。它还提示实质选择的目标和后继状态完全相同的情况，供编辑复核。

它不检查原文是否好看，不执行 UI，不检查存档事务或资产，也不自动懂人物心理。它没有直接读取本仓库。导出模型漏字段、漏条件或错误简化后，模型 PASS 可能毫无意义，所以必须做适配一致性验证。

### 13.2 接入而不是迁移引擎

由 agent 定位现有引擎，增加薄导出层，把发布内容转换为检查模型；禁止为了适配工具而改写整个游戏架构。布尔、有限枚举和有界整数可直接表达。全局入口状态需真实；不要把真实无法获得的高好感作为默认初值。

此格式只支持选择边上的状态效果，没有隐式 onEnter。若原引擎有入场效果、自动分支、函数回调或随机结果，要显式展开成有限状态和自动继续节点，并证明顺序一致。无法忠实展开就标为 UNSUPPORTED 或 BLOCKED，改用原引擎回放测试；不能忽略这些逻辑后宣称覆盖完成。

所有影响路线、可见文本或选项的历史都需进入有限状态，或形成可证明等价的状态摘要。不能只保留好感，丢弃承诺、拒绝、知识和一次性事件。模型不支持的行为不等于游戏必须删除的行为。

### 13.3 一致性验证要求

导出模型与真实引擎使用同一快照。逐步比较同一初态和同一选择序列下的可选项 ID、目标节点、相关状态与文本变体。完整有限状态范围内可比较全部一步转移；只能抽样时如实写明样本、种子、漏测范围，不能称为等价证明。

每个结局的模型证据路径必须再交给真实引擎跑一遍。若模型能到而游戏不能到，先修适配或游戏，不选择更好看的报告。任何修改条件或文本依赖后重新导出、重新比对。

### 13.4 命令与报告

在包根目录执行：

```sh
python -m unittest discover -s tools -p 'test_*.py' -v
python tools/storycheck.py examples/synthetic_scene.json --out reports/example-check.json
```

实际接入后，由 agent 生成 `reports/repository-story.json`，再执行：

```sh
python tools/storycheck.py reports/repository-story.json --out reports/repository-check.json --max-states 50000 --max-edges 500000
```

退出码：0 为当前导出模型 PASS；1 为模型检查 FAIL；2 为搜索受限 INCOMPLETE；3 为输入输出错误。达到搜索上限不是通过，也不应把尚未发现的结局直接判作不存在。报告始终含 `production_release_status: NOT_ASSESSED`。

枚举状态的 PASS 只针对显式模型与有限域。自由文本、真实时间、网络回调等不能被随意离散化为一个默认值。没有完整覆盖证据时，发布说明写清剩余范围。

## 14｜不招测试玩家的验收方式

采用四层证据，不用其中一层冒充另外三层：源码静态检查；真实引擎状态与路径回放；实际界面的端到端操作；逐场编辑审读。

逐场编辑审读要分别从“第一次玩、没有作者知识”和“知道全部事实、找矛盾”的视角完成。角色线路换位读，检查是否只有名字不同。模型自评只能形成修改线索，不是玩家喜欢程度或留存率数据。

浏览器版可使用项目已有端到端框架；若采用 Playwright，其官方文档支持跨 Chromium、Firefox、WebKit 和移动视口配置 [S2]。但模拟手机与 WebKit 不等于实机 Safari 验证，报告应准确命名环境。非浏览器游戏采用真实目标引擎的自动化能力，不照抄 Web 测试命令。

本包 80 项用例的初始状态都是 NOT_RUN。只有实际执行、保存日志或审读证据后才能改为 PASS。SKIP 必须说明功能确实不存在，BLOCKED 必须说明环境或模型缺口；不能用 SKIP 规避现有功能。

发布目标是：P0 为零；P1 全部关闭或从正式发布范围中移除并消除入口；所有发布结局真实可达；保存恢复无已知破坏性缺陷；主要界面可操作；关键故事问题收束。不能从这些条件推导“肯定留住用户”。

## 15｜最终应交付的成果与自查

实际仓库实施完成后交付：基线记录及完整 commit；源文件修改清单与差异；逐场审稿及完整关键场景替换稿；事实/知识/选择账本；适配覆盖说明；每个结局的真实回放；80 项验收状态及证据；构建日志；剩余风险；发布候选或补丁。

agent 最终说明必须回答：改了什么具体场景与机制？哪些选择现在有不同后果？删掉了哪些冗余且事实保留在哪里？哪些旧存档仍可用？哪些测试真跑过？哪些条件受限？是否真的修改了 GitHub？不要只写“体验显著提升、台词更加自然”。

不要新增与本轮目标无关的聊天 AI、抽卡、体力、广告、每日任务、账号或付费墙来掩盖内容问题。已有这些系统时仅修复与当前体验有关的缺陷，不擅自删除商业配置。

最终逐项确认：没有别的仓库内容；没有捏造源文件；没有把示例植入正式剧情；没有删测试掩盖失败；没有把模型 PASS 写成真实游戏通过；没有把自动回放写成玩家验证；没有在没有权限时声称已推送。
